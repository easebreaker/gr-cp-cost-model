# 10 · 预留升级位：性能模型 × scaling law

这一篇不汇报结果，它定义**下一步长什么样**，以及现在这套东西为什么已经够用。

---

## 0. 为什么升级路径必须是这个，不是别的

性能模型单独做，会被问两个问题：**"这不就是 profile + 拟合？"** 和 **"这个预测改变了什么决策？"**

第二个问题只有一个诚实的答案：**配置选择**。而配置选择里最有价值的那个决定是：

> 同样的卡、同样的工期，是买**更长的序列**、买**更大的模型**、还是买**更多数据**？

回答它需要两半：成本（已有）+ 质量（待建）。所以升级路径不是"再加一个模型"，而是**把已有的成本模型接到质量曲线上**。

## 1. 一个必须先说清的结构事实：CP 不是吞吐杠杆

这是整个 D 层的地基，而且它已经能用现有代码算出来。

对 `P` 张卡切成 `P/cp` 个副本、每个副本处理长度 `T`：

```
tokens/hour      = (P/cp) · B · T / t_step(cp, T)
GPU-hours for D  = D · cp · t_step(cp, T) / (B·T·3600)        ← P 抵消
```

关键在于 **`cp · t_step` 这个乘积**。即使加速比完美线性（`t_step(cp)=t_step(1)/cp`），乘积不变 —— 每个 token 的成本一模一样，**CP 什么都没买到**，只买到了"这么长的 `T` 能放进显存"。现实中 `t_step(cp) > t_step(1)/cp`，所以 CP 让每个 token **更贵**。

实算（`mtgr-large`, `T=4096`, 64 卡, 910B 参数）：

```
 cp   step ms  speedup   tok/GPUh  vs cp=1
  1    395.02     1.00   1194.512M     1.00x
  2    271.95     1.45    867.544M     0.73x
  4    216.17     1.83    545.702M     0.46x
  8    195.78     2.02    301.264M     0.25x
```

**结论：CP 是可行性杠杆和墙钟杠杆，不是 GPU-hour 杠杆。** 所以在固定 GPU-hour 预算下，CP 唯一能赢的方式是"它买到的长度带来的质量增益，超过它损失的吞吐"。

这一句话就把整个 D 层的问题定死了，也让"CP 好不好"这类提问失去意义 —— 要看在哪个 regime。

## 2. 三个 regime，边界都可测

| regime | 判据 | CP 的角色 |
|---|---|---|
| **短工期** | 显存够用，`cp=1` 能装下目标 `T` | 纯损失，别用 |
| **撞显存墙** | 目标 `T` 只有 `cp>1` 装得下 | **强制**，问题变成"选哪个 cp" |
| **长度饱和** | `alpha` 的收益已在当前 `T` 兑完 | 买长度不划算，退回更短的 `T` |

第三个 regime 是最反直觉、也最值得写进论文的：**把序列从 8K 拉到 32K 需要 cp=8，吞吐掉到 25%，而 `alpha≈0.38` 时长度收益早就在 8K 附近饱和了。** 结果是：显存墙和收益饱和点之间存在一个"最优长度窗口"，窗口宽度由 `alpha` 决定。

## 3. 门槛值：和 `c*` 同构的一个数

把"用 CP 换 c 倍长度"写成两个量之比：

```
长度收益  = A_L·[(l_ref/T)^alpha − (l_ref/(cT))^alpha]
数据损失  = A_D·[(d_ref/D)^gamma − (d_ref/(fD))^gamma]        f = 吞吐比 < 1
```

CP 划算 ⟺ 长度收益 > 数据损失。只解出 `alpha` 的门槛：

```
  T=4096  B=32  64 NPUs  72 h
   cp  tokens(B)  tok ratio   T_long   alpha*
    2   3116.92       0.57     8192    0.150
    4   1642.30       0.30    16384    0.212
    8    819.10       0.15    32768    never
```

读法：**`alpha` 只要大于 0.15，用 cp=2 把长度翻倍就划算；大于 0.21 时 cp=4 也划算；但从 4K 拉到 32K（cp=8）在任何 `alpha` 下都不划算** —— 吞吐掉 85%，任何幂律都补不回来。

`alpha*` 只依赖一个能从不带 CP 的长度扫描里拟合出来的指数。所以这是一个"测一次、算一个门槛、据此排除掉大部分配置空间"的结果，形状和 `c* = F/BW` 一模一样。

⚠️ **一个必须小心的地方**：`alpha` 的收益对 `alpha` 不单调 —— `alpha→0` 时没有收益，`alpha→∞` 时收益已在当前长度兑完，中间才有峰值。所以求门槛必须**扫描首次穿越**，不能用二分。（第一版就是这么错的，`tests/test_quality.py::test_length_gain_is_not_monotone_in_alpha` 盯着它。）

## 4. 两个不同的问题，很容易混

这是组会上最容易被抓的点，必须分开讲：

**（a）同一个 `T` 下，`cp>1` 比 `cp=1` 好吗？**
永远不好。同长度、更少 token，严格更差。

```
      T       cp=1      cp=2      cp=4      cp=8
   4096     0.7025    0.7013    0.6993         -
   8192     0.7049    0.7041    0.7027    0.7002
  16384          -         -    0.7040    0.7021
```

**（b）`cp=2` 在 `2T` 下，比 `cp=1` 在 `T` 下好吗？**
看 `alpha`。这是 §3 的门槛表。

（b）成立不等于 CP 全局最优 —— 中等长度 + `cp=1` 仍然可能赢，因为长度收益先饱和了。**只有分清 (a) 和 (b)，"CP 值不值"才是一个可回答的问题。**

## 5. 质量侧怎么写（`quality.py`）

Chinchilla 式的加性亏空：

```
Q(L, m, D) = Q_inf − A_L(l_ref/L)^alpha − A_m(m_ref/m)^beta − A_D(d_ref/D)^gamma
```

三条选择理由，以及各自的代价：

| 选择 | 理由 | 代价 |
|---|---|---|
| 加性亏空 | 已发表的 GR 曲线（LONGER Fig. 4、MTGR 三个尺寸）都显示饱和 | 它断言三条杠杆在亏空空间里**一比一互相替代**，这是最弱的一步 |
| 三个独立幂律 | 每个指数都能从单变量扫描里单独估 | 忽略了杠杆间的交互（更长序列可能需要更大模型才吃得住） |
| 上界 `Q_inf` | 可解释、可检查（不能超过 1） | 需要外推，而 `Q_inf` 恰是最难估的参数 |

**`fit_quality` 会返回 `identifiable` 标志**：只有三条杠杆都变化超过 1.2× 时才是 `True`。只扫长度的网格会"收敛"得很好，但 `a_size`、`a_data` 停在初值上，算出来的前沿由任意常数驱动。这和 `memory.fit_memory` 是同一个陷阱。

## 6. 要什么数据

| 用途 | 数据 | 能否用公开数据 |
|---|---|---|
| 成本侧 | 已有 12 组标定 + 20 组验证 | 不能，必须自测 |
| 记忆墙 | 每档 `cp` 的 `T_max`（两次不同 chunk 长度起） | 不能 |
| `alpha` | 长度扫描（≥5 点，跨 16×，无 CP） | **能**：LONGER Fig. 4 是幂律 |
| `beta` | 2–3 个尺寸 | **能**：MTGR 给了 small/medium/large |
| `gamma` | 2–3 个 token 预算 | 半能（论文通常只报一个点） |
| 交叉验证 | 一个 (L, m) 组合，未参与拟合 | 不能 |

所以**最快的一条路**：`alpha` 和 `beta` 从公开曲线拟合，`gamma` 自己小规模补，`Q_inf` 用最大的公开点约束。这样质量侧的成本接近零，而成本侧本来就要测。

## 7. 三档贡献与 go / no-go

| 档 | 交付物 | 风险 |
|---|---|---|
| 1（稳） | 跨模型、CP-aware 的成本模型 + 四路归因 | 低，不需要质量数据 |
| 2（中） | + 配置搜索：给定显存和工期，选出 `(T, cp, kernel, batch)` | 低，Vidur-Search 已立先例 |
| 3（进取） | + 质量曲线，给出 `(GPU-hours, quality)` 前沿与三杠杆排序 | 高，取决于 §5 的替代假设 |

**建议顺序：先做 1，再做 2，只在 1 和 2 都稳了之后碰 3。** 三档是严格的包含关系，所以不存在"做小了"的问题。

判据（在看数据之前定下来）：

| 结果 | 判定 |
|---|---|
| 档 1 的 held-out MAPE < 15%、排序 > 90%、跨模型 < 20% | 三档都可行 |
| 档 1 通过但平坦区排序差 | 只做档 1；模型是描述性的，不是决策性的 |
| 质量侧 `identifiable=False` | 档 3 降级为 case study，只报 `alpha*` 门槛，不报前沿 |
| 加成性假设被证伪（前沿排序在有无交叉项时翻转） | 档 3 需换设计（联合损失/多目标），退回档 2 |
| 换个 kernel 后 `c_star` 移动 > 3× | 撤"标定一次"，档 1/2 仍成立但缩水 |

## 8. 现在就该做的一件小事

`python3 scripts/frontier_demo.py` 会在合成参数上跑完整个组合，输出三张表：

1. CP 的吞吐代价（§1）
2. 每档 `cp` 的可行长度（§2 的显存墙）
3. `alpha*` 门槛 + 固定工期下的最优配置（§3、§4）

它现在**不是结果** —— 质量律是占位的（`sourced=False`，每次输出都会打 WARNING）。它的用处是：**在拿到真实数据之前，先把"哪种结果会出现"的框架搭好**，这样拿到数据时不是从零开始猜。

一个可以直接说的结论，即使质量律是占位的：**CP=8 在这个吞吐代价下永远不划算。** 因为这条结论只依赖 `f=0.15` 这一个可测量的数，与质量律的具体形状无关。这类"不依赖占位参数"的结论，在组会上最安全。
